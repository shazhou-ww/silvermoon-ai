# Deployment

实现已按精确 Inner revision 接受，本契约进入部署准备。候选实际路径来自仓库部署配置；生产操作仍需明确范围授权，进入 deploying 或普通同步 main 不等于已经部署。当前外部事实见[部署准备证据](./Deployment-Evidence.md)，不复述 Inner 实现。

## 目标与操作边界

- 配置目标：Worker `silvermoon-relay`，域名 `relay.silvermoon.work`；D1 `silvermoon-relay`；Pages 项目 `silvermoon-work`，界面域名 `silvermoon.work`。
- 正式服务升级由将待发布主线提交整合到 `release` 后的 GitHub Actions 驱动；不能以更新 `main`、本地构建或 dry run 代替部署。
- 仓库流水线不发布 npm。`@silvermoon-ai/connector` 包发布和实际设备升级必须另行明确范围；旧 connector 缺少确认时只能查看历史，升级期间不能许诺远程发送继续可用。
- 用户已明确授权通过 release 部署 Relay/Web 与数据库迁移；connector npm 发布及实际设备替换仍不在本次授权范围。实际执行与证据按下列步骤推进，不把服务上线当作设备端验证完成。

## Steps

### D-S01: 准备兼容升级与恢复条件

明确目标环境、实际迁移、Relay/Web 与 connector 版本及升级顺序；区分仓库同步与包发布，确认备份、恢复条件和发布范围。

1. 先同步本部署契约到 primary，记录其稳定 deploymentRevision，再以该版本核对待发布源码提交、当前 main 的质量流水线结果、release 当前 tip 与现有服务/设备版本。
2. 服务升级沿用[仓库流水线](../../../../.github/workflows/check-and-deploy.yml)：检查通过后先应用迁移 0010，后 Worker/Durable Object，最后 Pages。Connector 升级必须匹配当前确认协议，不能只部署 Web 就视为功能完整。
3. 执行前确认生产操作授权及已有数据库备份/可恢复条件。回退不能删除新字段或丢弃命令/会话历史；必要时暂停远程操作、保留已保存正文并走向前修复。具体备份时点与旧版本取自真实环境，不虚构已存在备份。

本次待发布基线包括已经通过 main CI 的 `0e8f3d85b7a8a6a07a701e7bbe2b969846969e65` 及后续只改变事件/本契约的提交；release 集成主线是累积发布，包含同步后的登录与设置工作区等既有主线变更。执行前再次核对源码和 workflow 未被未验证的并发提交改变；release 流水线还须完整检查通过才进入部署。

### D-S02: 应用外部升级

按已同步的部署契约应用迁移与服务/设备更新，保留历史身份及数据；旧 connector 未确认状态显式提示，不隐式放开操作。

只在范围授权、目标与恢复条件明确后，普通整合并推送 release 触发部署。记录 release commit、对应 Actions run、D1 迁移应答、Worker/Pages 版本与实际设备 connector 的来源/版本。若 npm 发布未获授权，可只记录待完成的设备升级，不伪称完整发布；不能为了设备更新修改已接受的 Inner deliverables。

本次在 operation-owned release worktree 中整合指定主线，执行 Silvermoon 工作区/暂存检查后普通提交并推送 release；不切换或覆盖用户当前 main 工作区、不修改应用 deliverables、不 force-push。实际 connector 版本未知时 D-S02 与 D-AC01 不据服务部分完成而全部勾选。

### D-S03: 验证真实离线与重连

在目标设备验证混合列表、断网、重连确认、历史读取、主动继续和未确认结果；记录实际环境、版本与可复核结果，不以 mocked API 或构建代替外部证据。

使用用户授权的真实设备与非敏感测试会话验证：在线+离线混合列表、实际断连、旧快照隐藏、已打开详情与草稿、重连确认期间禁用发送、当前能力确认后主动继续，以及已有等待输入选项的兼容行为。不自动发送用户已有草稿，不故意重复可能已经执行的命令；仅对专用测试命令检查未知结果与补传。没有可用设备/账号授权时保留 D 项未完成。

## Acceptance criteria

### D-AC01: 实际版本与迁移可核对

取得目标数据库迁移和 Relay/Web/connector 版本的外部证据，确认升级顺序及现有身份和历史没有丢失。

证明方式：成功的 release 部署 run 与 commit 对应，远程迁移记录包含 0010，服务版本与设备版本可复核，升级前后抽样业务身份/已保存历史一致。main 的 check run 成功只证明质量 gate，不满足本条部署完成。

### D-AC02: 真设备状态与操作语义正确

通过真实断网与重连记录证明离线仅显示 Offline、旧快照不计数、已打开页面保留、草稿不自动发送；本次连接能力确认后才允许主动操作。

证明方式：同一实际 Session 的在线、离线、重连未确认、确认后四个状态的截图/观测与操作结果，包含关键词 AND 状态与当前 facet、离线历史入口、读取位置和本地草稿。无可信执行观测的元数据历史记录保持未知，但确认可继续能力后可明确主动操作；记录能力不等于执行成功。

### D-AC03: 失败与兼容路径可理解

记录同步失败、未知结果、旧 connector 和历史读取的实际反馈；核实不自动重发且已有可复核结果正确归属，无法恢复的结果继续明确未知。

证明方式：专用测试命令的执行次数与原命令归属、至少一个旧/缺少确认 connector 的只读兼容反馈，以及状态/历史同步错误的可理解提示和重试结果。真实环境无法安全诱发的边界明确记为未验证，不把 Inner 自动化通过结果重复当作外部证据。
