# Deployment

实现已按精确 Inner revision 接受。本轮部署范围经用户再次明确：网站、Relay 和数据库迁移；暂不发布 connector，也不以设备升级作为本轮部署验收前提。真实结果见[部署证据](./Deployment-Evidence.md)，不复述 Inner 实现。

## 目标与操作边界

- 配置目标：Worker `silvermoon-relay`，域名 `relay.silvermoon.work`；D1 `silvermoon-relay`；Pages 项目 `silvermoon-work`，界面域名 `silvermoon.work`。
- 正式服务升级由将待发布主线提交整合到 `release` 后的 GitHub Actions 驱动；不能以更新 `main`、本地构建或 dry run 代替部署。
- 用户于 2026-10-11 明确“connector 暂时不发布，网站可以部署，其他 deployment 验收做完即可 accept”。仓库流水线不发布 npm；包发布、实际设备替换及依赖新 connector 的真实执行／断网测试均移出本轮部署验收范围，不伪称它们已完成。
- 网站在当前旧 connector 环境下必须诚实提示缺少确认、禁止未确认的远程操作，并允许读取已授权的保存内容；不能为了本轮验收放宽状态／能力门槛或制造连接确认。

## Steps

### D-S01: 准备兼容升级与恢复条件

明确目标环境、迁移、Relay/Web 版本、质量 gate 和恢复条件；区分已部署服务与本轮排除的 connector 发布，保留旧设备兼容限制。

1. 先同步本部署契约到 primary，记录其稳定 deploymentRevision，再以该版本核对发布源码、release 成功流水线、服务版本、迁移记录与旧 connector 兼容状态。
2. 服务升级沿用[仓库流水线](../../../../.github/workflows/check-and-deploy.yml)：检查通过后先应用迁移 0010，后 Worker/Durable Object，最后 Pages。已匹配源码部署成功时复用实际结果，不为部署说明重复推送 release。新 connector 才具备的操作仍标为本轮范围外。
3. 执行前确认生产操作授权及已有数据库备份/可恢复条件。回退不能删除新字段或丢弃命令/会话历史；必要时暂停远程操作、保留已保存正文并走向前修复。具体备份时点与旧版本取自真实环境，不虚构已存在备份。

本次待发布基线包括已经通过 main CI 的 `0e8f3d85b7a8a6a07a701e7bbe2b969846969e65` 及后续只改变事件/本契约的提交；release 集成主线是累积发布，包含同步后的登录与设置工作区等既有主线变更。执行前再次核对源码和 workflow 未被未验证的并发提交改变；release 流水线还须完整检查通过才进入部署。

### D-S02: 应用外部升级

核对已授权的实际数据库、Relay 与 Web 升级，保留历史身份及数据；旧 connector 未确认状态显式提示，不隐式放开操作。

记录 release commit、成功 Actions run、D1 迁移应答、Worker/Pages 版本和升级前后数据保留的外部证据。只核对现有 connector 缺少确认的兼容反馈，不发布包、不替换设备、不触发用户 agent 命令；不修改已接受的 Inner deliverables。

若需要新的服务升级，用 operation-owned release worktree 整合指定主线，经 Silvermoon 工作区/暂存检查后普通提交并推送；不覆盖用户 main 工作区、不 force-push。已有匹配的成功发布可完成本条服务范围，不再以新 connector 发布阻塞。

若并发 release 已包含相同待发布应用源码，核对差异和成功 run 后可以复用实际部署结果，不为同步部署说明而取消重跑同源码流水线；必须明确记录触发来源、本次验证范围及尚未升级的设备范围。

### D-S03: 验证线上列表与旧设备兼容

在实际已登录生产网站验证默认隐藏、菜单、关键词与状态筛选、离线历史、详情、草稿、移动布局和现有未确认设备操作限制，记录可复核的线上结果，不使用 mock 或构建替代。

使用用户登录的当前账号，仅读取授权 Session，不发送、创建或重试设备命令。可以编辑并清理本轮专用草稿、切换列表与本地显示选项；不能覆盖用户原草稿。核对旧 connector 提示与发送禁用，已保存正文仍可读，浏览器刷新不产生业务命令。没有已登录浏览器时暂停本条，不能从 D1 读数推断 UI 验证通过。

依赖新 connector 的主动继续、状态成功恢复、故意断连与真实执行结果补传留待后续设备升级验证，不作为本轮 D-S03 的条件，也不标成通过。

## Acceptance criteria

### D-AC01: 实际版本与迁移可核对

取得目标数据库迁移和 Relay/Web 版本的外部证据，确认升级顺序与现有数据保留；明确 connector 本轮未发布，不要求新设备版本。

证明方式：成功 release run 与源码对应、远程迁移包含 0010、Worker/Pages 版本可复核；迁移前后聚合数量未减少并在授权网站抽样读取既有历史。聚合一致不冒充逐条正文哈希一致；main check 成功不替代外部发布。

### D-AC02: 线上过滤与历史可见性一致

在真实生产网站证明默认隐藏离线、关键词 AND 状态、独立 facet 与离线 N、显式历史仅在 All、离线只显示 Offline，详情及本地草稿可用但不发送。

证明方式：授权已登录页面的列表/搜索/菜单/详情截图或聚合观测，桌面与窄屏无文档溢出；旧设备没有当前确认时三类计数不包含旧执行值。试用草稿不得发送或留下本轮内容，真实网络请求记录中无业务消息/创建调用。新 connector 运行态和成功恢复不包含在该标准中。

### D-AC03: 失败与兼容路径可理解

证明当前旧 connector 和未认证/不可确认路径的线上反馈诚实：显示更新要求、未确认不能发送、历史仍可读，不把旧状态或失败当成实时成功。

证明方式：至少一个 online/unsupported 设备的生产详情展示更新要求并禁用发送，offline 详情只显示 Offline，鉴权保护保持；不通过真业务命令制造未知结果或错误。实际状态失败重试、真设备断网、命令补传与发布后的新能力都明确范围外，只引用 Inner 证据作为实现背景，不计为本条外部通过结果。
