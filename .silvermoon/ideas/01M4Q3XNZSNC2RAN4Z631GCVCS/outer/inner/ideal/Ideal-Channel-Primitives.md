# Connector 请求原语：下行请求与对应反馈

## 文档定位

这是构想的评审支持材料，不是已接受的 wire 契约或产品实现。两个方向信道共同完成调用，按下行请求组织讨论；上行反馈与对应请求一起定义，不再维护独立的上行消息分类。具体字段、方法名与时间参数仍为候选。[现状清单](./Current-WebSocket-Primitives.md) 不变。

## 1. 两个方向，一套调用逻辑

上下行只按 Connector 与 Relay Service 之间的传输方向定义，不随请求、响应或消息内容改变。本文中的 Relay、“中继”均指 Relay Service：

| 信道 | 方向 | 职责 |
| --- | --- | --- |
| 下行信道 | Relay Service → Connector | 发出操作请求、状态读取及带等待的更新读取 |
| 上行信道 | Connector → Relay Service | 返回结果、错误、状态与历史批次，以及可选的短时续推 |

这是同一 WebSocket 上的方向分类，不要求两条物理连接。前端与 Relay Service、Connector 与本地 provider 的通信不沿用这两个方向术语，也不在此预设其传输。同步读取也属于下行请求，但不等于要求 Agent 执行工作。

- 单次操作：通过 requestId 关联一个结果或错误，明确成功是已接纳还是已执行。
- 持续观察：反复发出带 target、观察基准和最长等待时间的读取请求；同一 requestId 的流式反馈可分多包返回 events，等待超时则明确无更新。
- 低延迟优化：Connector 在响应后短时主动续推，不要求客户端预挂请求，也不建立长期 observe/unobserve 订阅。

多个请求的反馈可以交错。一次操作的接纳、Agent 执行终态与人工任务完成是不同事实。

## 2. 下行请求及对应反馈

以下五类是候选请求职责，不冻结 wire 方法名。各类请求明确输入意图、反馈内容、后续更新及失败边界；共性规则只在后文定义一次。

### 2.1 读取 Session 清单

- **请求什么：** target 指定设备/provider 的 Session 清单范围；首次读取、重新发现或等待清单新增/减少，必要时携带已有目录观察基准，不另指定 streamId。
- **返回什么：** 范围内的 Session 清单及完整当前摘要，说明覆盖范围与完成边界；分页不新增领域类型，清单与单 Session 读取使用相同摘要语义。
- **后续更新：** 继续读取可复用有界等待机制；不能只靠单个 Session 的变化通知证明目录已完整同步。目录是否适用短时续推留待实际需要确定，不默认创建订阅。
- **超时或失败：** 无更新超时、部分清单、同步失败与完整空目录可区分；一次清单缺项不证明 Session 已关闭、删除或应清除缓存。

### 2.2 读取／等待 Session 更新

- **请求什么：** target 指定来源设备、Session 及所需观察范围，携带已处理基准和最长等待时间；首次读取、历史补齐、断线恢复与等待后续更新采用同一原语，不另指定 streamId。
- **返回什么：** 按 target 返回当前摘要、历史批次或临时更新及其下一观察基准，同时说明覆盖进度、已知终点或缺口。同一 requestId 可关联多个 events 包，Relay Service 按稳定事件编号去重和排序，拼装截至声明终点的数组；批次不是持久事实身份，也不另设独立 history.sync 操作。
- **摘要边界：** 包括元数据、父子关系、规范化状态及必要原生说明、状态可信度、可写能力和当前待回答请求。候选优先使用完整摘要；没有待回答请求时显式清除旧提示，不把未知、未提供和明确不可写混为一谈。
- **历史边界：** 保留来源实际记录的消息、工具调用/结果、输入请求/回答、状态、错误与活动内容；调用和结果可以关联但不覆写。不是六个额外 wire 操作，也不要求 provider 补造缺失事实或统一 turn 生命周期。
- **后续更新：** 接收方续拉；Connector 可按第 4 节短时续推。同一历史记录经补拉或续推到达身份不变，临时预览采用独立版本，不能覆盖已确认内容。
- **超时或失败：** 等待超时只说明无更新；完整空历史、部分覆盖、基准失效、回源不可用和临时缓冲过期分别可识别。当前状态不能从旧 running/error 历史推断，旧连接观察不能确认新连接可写。

### 2.3 创建 Session

- **请求什么：** 指定设备/provider 及支持的创建参数，可包含初始输入；能力和参数限制显式声明。
- **返回什么：** 创建结果及新 Session 身份；是否已接纳初始输入需说明，不宣称初始回答已完成。
- **后续更新：** 使用该 Session 身份读取／等待更新，也可在后续清单中发现；创建操作不自动建立长期观察。
- **超时或失败：** 不支持或创建被拒绝返回明确错误；断线后创建结果未知不能直接判失败重建，按约定去重或查询恢复。

### 2.4 发送消息

- **请求什么：** 给明确 Session 发送用户内容，保留调用关联；读取当前能力不代替 provider 的最终接纳判断。
- **返回什么：** provider 接纳或拒绝的结果，不把已接纳解释为 Agent 已执行完毕，也不由前端直接写入权威历史。
- **后续更新：** 后续执行和消息事实通过读取／等待 Session 更新获取；来源支持时可关联原 requestId，事实不依赖该响应先到达。
- **超时或失败：** 无能力、参数错误或拒绝有明确反馈；结果未知不得盲目重发非幂等消息，后续 Agent 执行失败与本次接纳结果分开。

### 2.5 回答输入请求

- **请求什么：** 指定 Session、明确的 inputRequestId 及类型化回答，不靠当前气泡位置猜测目标。
- **返回什么：** 回答接纳或拒绝结果，不宣称 Agent 已继续执行或完成；不支持结构化回答不能默默降级为普通文本。
- **后续更新：** 读取／等待更新取得输入请求的后续事实及当前 pending 状态；接纳结果不替代请求结束事实。
- **超时或失败：** 请求已失效、不支持或回答被拒绝应有明确结果；断线导致未知时遵循操作去重与恢复规则，不自动重复回答。

执行取消、配置修改和命令结果查询属于按真实能力另定的扩展请求，不因已有方向信道就默认暴露 provider 的全部操作。停止观察与取消执行不是同一请求。

## 3. 共性读取规则：补历史与等待更新

下行请求的语义是：“我已观察到这个 target 的某个状态，有更新时继续通知我。”target 表达观察范围与来源，例如某个 Session 的更新，或某设备的 Session 清单变化；观察基准表达该范围内已处理的位置或版本，不能仅用墙钟时间。

1. 有积压时立即返回数据和覆盖信息，可分多包发送；同一 requestId 下合并各包，不必逐条支付 round trip 或等待整份数组才消费。
2. 没有更新时等待，直到有更新或达到最长等待时间。等待超时返回无更新，基准不变；它不证明 Session 历史为空或 Agent 已停止。
3. 接收方处理后及时续拉，不等待 UI 渲染；不再续拉即可停止观察，已挂起请求和可选续推在有界时间内结束。
4. 重连、缓存未命中和补洞使用同一读取原语。后续请求可以使用新 requestId，仍以同一 target 和已处理基准续读；失效基准必须显式报告并重新同步，不能把新来源的编号拼接到旧来源记录。

“同一原语”不意味着所有内容共用一个数字 cursor：

| 内容 | 观察与恢复边界 |
| --- | --- |
| 不可变历史 | JSONL 级记录的有序 eventId 同时表达身份与位置；可以重放，不另要求 sequence |
| 当前 Session 摘要或目录 | 有来源、新鲜度、版本和覆盖范围的当前观察；不伪装成永久历史 |
| 临时实时更新 | 独立的短期观察位置或版本；可缓冲、过期，不占历史游标 |

观察基准的实际编码、单次批量上限及当前摘要的版本来源留待实施细化。完整空历史、没有新更新、部分覆盖和回源不可用必须可区分。

多包拼装必须知道覆盖范围或完成边界：“完整数组”只指截至某个声明位置完整，不意味着 Session 永远没有后续事件。首包、最大已见 eventId 或接收方本地等待超时都不能单独证明完整；存在缺口时不推进已处理基准。不要求编号为连续整数，缺口根据来源声明的覆盖范围判断。

## 4. 共性优化：Connector 短时主动续推

用户提出的优化：Connector 刚返回某个 Session 的更新后，若短窗口内继续有变化，就沿上行信道继续发送，不等待下一次下行请求。

候选约束：

- 首包到达结束“等待首个更新”，不等于该 requestId 的全部反馈已结束。后续包与有界续推沿用原 requestId，绑定同一 target；流式反馈的范围和结束边界必须可识别，不能把每包当成独立 RPC 终态结果。
- Connector 可以不续推；正确性和历史恢复只依赖后续读取。接收方不再关注时可以丢弃续推，不必发送 unobserve。
- 续拉与续推可以重叠，甚至关联不同 requestId。先按请求关联组装，再按 target 的来源范围及 eventId 去重、排序历史；临时更新按独立版本处理。批次边界可以变化，同一历史记录的有序编号与内容不变。
- 续推窗口有空闲截止时间及最长总时限，连接失效后旧来源通知不再确认当前状态；流控与背压必须有界。具体时长、额度和是否续窗尚未决定。
- 丢弃续推不表示已处理，也不推进恢复基准。再次读取可补回仍可用的内容；临时缓冲已过期则报告缺口，并恢复当前可用状态。
- 临时预览不能覆盖已确认历史或更新的观察版本；忽略通知不等于自动把该通知当作可信事实。

这不是新的持久订阅实体，也不把停止观察解释为停止 Agent 执行。长期推送和显式 cancel/unobserve 不作为当前方案的必需原语。

## 5. 共性身份与归约

| 身份 | 作用 |
| --- | --- |
| requestId | 标识一次读取或操作调用，关联其单次结果、多包 events 及有界续推；不作为事件身份或跨请求恢复位置 |
| target | 表达来源与观察范围，例如某个 Session 或某设备的 Session 清单变化；替代必需的独立 streamId |
| eventId | 在同一 target 的来源范围内，稳定且有序地标识一个事件，兼任身份与顺序位置；不另要求 sequence，不使用墙钟时间猜测顺序 |
| 观察基准 / cursor | 表达该 target 下已处理的覆盖位置或状态版本，跨 requestId 续读；不等于最大已见 eventId |
| sessionId / messageId / partId 等 | 标识被描述的对象，不代替事实身份 |
| 当前观察或临时更新的来源与版本 | 识别新鲜度、重复及过期更新；不冒充历史位置 |

不再要求单独建立 EVENT_STREAM 或 streamId；流式是一次请求的反馈方式，持续观察范围由 target 描述，不把 requestId 改成持久流身份。同一 requestId 必须绑定同一 target 与请求参数。

合并 eventId 与 sequence 的前提是事件编号在相同 target、相同来源范围内唯一且有稳定排序，补拉、重传和续推不变，同编号不能绑定不同内容；不要求跨设备全局唯一或连续整数。来源重建或编号重置时旧观察基准必须明确失效，不能复用旧缓存拼接。具体编号类型、比较规则、provider 稳定记录保证与来源失效编码留待实施，不得为统一格式虚构缺失事实。

上行包的 requestId 是本次读取的传输关联，不是“哪个操作造成该事实”的因果关联；同一事实可以出现在多次读取中。临时预览的新版本不能复用旧通知身份去重，否则会把新变化当作重复丢掉。

传输 envelope 负责关联和同步，领域原语表达事实，UI projection 负责呈现；不能按气泡数量定义历史事件。历史类别按 message/tool/input/status/error/activity 的职责讨论，不强制每个 provider 全部支持。

## 6. 共性历史缓存与恢复

- 设备侧是事实生产边界，中继与客户端只能转发、缓存和投影；不能凭发送意图确认 Agent 已收到。
- 已发布 JSONL 级历史不可变，重复幂等，身份冲突显式失败。它不包含逐 token/chunk 的中间预览；不要求 wire 使用 JSONL。
- 恢复基准仅从连续处理的位置推进，不能把最大已见位置当作完整水位。当前状态快照也不能伪造此前 transcript。
- 中继按整个 Session 淘汰历史缓存，不仅保留尾部并声称完整；淘汰时失效依赖它的覆盖标记和恢复基准，目录发现信息可以独立存在。
- 缓存未命中时回源，分批补齐前明确部分覆盖。设备不可用或来源已清理时明确不可用，不能返回成功形状的空历史。
- 接收方自己仍保有的连续历史可继续使用；中继淘汰不自动否定它，也不等于关闭 Session 或清除命令去重记录。

临时更新缓冲有独立生命周期，不适用完整历史的整 Session 保留保证。缓冲保留期、允许合并或丢失哪些临时内容、缺口后的当前状态恢复方式尚未确定。不可变不等于永久保留。

## 7. 共性失败与结果关联

| 反馈 | 含义 |
| --- | --- |
| 操作结果或 error | 对应 requestId，说明接纳、拒绝或方法错误 |
| 操作结果未知 | 断线或超时后不能确认是否执行；不自动判失败并重发非幂等命令 |
| Agent 历史事实 | 可与请求有可选因果关联，但不依赖请求先到达，也不修改已返回的接纳结果 |
| 同步覆盖或不可用 | 说明读取范围的完整性和恢复能力，不等于领域执行失败 |

requestId 不自动提供 exactly-once；去重责任、参数绑定与结果保留期待定。重复读取不应触发新的 Agent 工作。

## 8. 当前功能覆盖对照

从原独立上行分类材料迁入必要的覆盖检查，按请求归属而非上行消息类型组织。源码调查基线为 `0d25cd8fd4722815e07e3b2a467871c464158f8e`，不是当前持续前进的 remote main；详细事实与源码索引见 [现状清单](./Current-WebSocket-Primitives.md)。下表说明表达能力，不证明目标模型已实现。

| 当前功能或状态 | 请求归属与反馈 | 保留的边界或缺口 |
| --- | --- | --- |
| 初次发现、重连刷新、Session 搜索与设备分组 | 读取 Session 清单 | 清单声明范围与完成边界，不用变化通知代替完整发现 |
| 新建 Session 出现在列表 | 创建 Session，后续读取清单或 Session 更新 | 无需独立 created 上行操作；创建结果不等于初始执行完成 |
| 标题、父子关系、排序时间及列表摘要 | 两类读取共享当前摘要 | 不依赖中继保有完整历史；历史淘汰不等于删除目录 |
| queued/running/waiting/idle/failed | 读取／等待 Session 更新的当前状态 | 不为每个值新建操作；queued 在 schema/UI 存在不承诺每个 provider 都产出 |
| closed/归档、gone/不可用 | 读取／等待 Session 更新的当前摘要 | 关闭、归档和消失不等于删除历史，不预设新生命周期分类 |
| unknown、状态可信度与旧连接观察 | 两类读取的来源与可信度 | 未知不能默认 idle；历史事实不确认当前状态或能力 |
| offline/removed/unknown-device | 中继设备及连接信息，影响读取可用性 | 不伪造 Connector 发出的 Session 历史事实 |
| syncing/sync-failed/unsupported/unconfirmed | 清单完成边界、调用反馈与连接确认 | 保持同步失败可见，旧观察失效，不新增 Session 领域事实 |
| follow-up 可写性 | Session 当前摘要与发送消息结果 | 联合连接确认、设备能力与 Session 能力，不仅依赖 running/idle |
| 等待输入、问题与答案 | Session 当前摘要、历史与回答输入请求 | 显式清除 pending；当前摘要与 worker pending 推导未完全直通，不能只换名宣称完成 |
| transcript、工具折叠与计数 | 读取／等待更新的消息/工具历史及来源关联 | 保留调用/结果、分段与显示顺序，快照覆盖不是不可变历史保证 |
| activity、system、error | 读取／等待更新中的实际历史内容 | 不因精简丢信息；活动与临时进度区分，历史错误不代替 RPC 错误 |
| 离线或设备删除后的旧历史 | Session 读取命中缓存则可读，未命中回源 | 可淘汰缓存有意改变长期可读保证；不可用显式报告，相关 UX 须后续确认 |
| 历史加载、空历史与回源失败 | Session 读取的批次、范围及完整性反馈 | 当前 commandCompleted/history_synced_at 不证明连续完整覆盖，event upsert 不证明不可变性 |
| 临时预览与连续更新延迟 | Session 带等待读取及可选短时续推 | 与历史使用独立版本及保留保证，过期报告缺口，不引入长期订阅 |

尚无必要性证据的独立 turn 生命周期、通用消息修订、附件生命周期或人工工作状态不预先扩展。上行字段是否合并编码留待实施，不再以消息类型数量作为完整性目标。

## 待定事项与范围

当前批准方向的焦点是两个方向信道、target + 观察基准、requestId 多包反馈、有序 eventId 合并身份与位置，以及 Connector 有界续推；不冻结完整 schema、时间阈值或版本迁移方案。
