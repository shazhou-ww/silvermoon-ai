# 理想信道：Session 状态信道、命令信道与可订阅消息信道

## 文档定位

这是讨论草案，不是实现方案或已批准 wire 契约。字段名、事件名和命令名均为候选，不对应当前 schema 的变更。

**用户在本轮明确提出的方向：**

1. 同一条 WebSocket 明确划分三个逻辑信道：第一信道为 Session 状态信道，第二信道为命令信道，第三信道为可订阅消息信道。
2. 状态同步基于历史不可变的 event stream，业务事实单向传播：设备 → 中继 → 前端。
3. 历史不可变性允许中继及客户端缓存各设备、各 Session 的事件历史。
4. 用户发给 Agent 的消息属于命令，而不是前端直接写入状态流。
5. 命令交互采用典型 RPC 思路，需要明确支持的命令。
6. 中继以可淘汰缓存为主，完整历史依赖设备回源；缓存淘汰以整个 Session 为单位，不截断已缓存 Session 的旧历史。
7. 不可变历史采用通常 Agent Session JSONL 的记录粒度，不包含逐 token、逐 chunk 等流式中间状态；不要求原样重放所有实时更新。
8. 第三信道承载临时实时消息；由第二信道发起对某个 Session 的实时更新订阅或取消订阅，Connector 上行推送对应 Session 的临时更新。该能力仅记录为后续 TODO，本期不实现，不冻结订阅生命周期或时序规则。
9. 以 Connector 与中继的连接为准，第一、第三信道是 Connector → 中继的单向上行信道；第二信道是请求下行、回复上行的双向信道。需要反向传递的同步控制也归第二信道，不在第一、第三信道增加逆向业务消息。

**本草案补充的候选规则**不等于用户已接受。中继缓存角色、整 Session 淘汰及历史不含流式中间状态的方向已明确；设备/provider 如何提供稳定的历史记录、序号分配、具体事件种类与命令集合仍未决定。“JSONL 粒度”指历史语义，不要求 wire 使用 JSONL，也不把某个 provider 的文件格式直接冻结为公共协议。[现状清单](./Current-WebSocket-Primitives.md) 保持不变；身份与生命周期的集中评审见 [业务模型评审](./Business-Data-Model-Review.md)。

一个物理连接中的三类逻辑消息，不要求拆成三条物理 WebSocket；前端到中继采用什么传输也不在本轮预设。本期讨论重点仍是下述历史状态同步与命令 RPC 两部分；第三类责任仅记录方向和 TODO。

| 信道 | 固定讨论名称 | 职责与方向 | 本期范围 |
| --- | --- | --- | --- |
| 第一信道 | Session 状态信道 | 单向上行：Connector → 中继，同步 Session 目录、状态和 JSONL 级历史，再由中继供前端消费 | 收敛原语 |
| 第二信道 | 命令信道 | 双向：中继 → Connector 下发请求，Connector → 中继返回 RPC 结果/错误；包括同步控制及未来第三信道订阅控制 | 收敛核心命令 |
| 第三信道 | 可订阅消息信道 | 单向上行：Connector → 中继，推送已订阅 Session 的临时实时消息，不进入历史缓存或历史游标 | 后续 TODO，不在本期实现 |

三个信道是语义分类，不表示三个连接，也不预设 wire 的字段或信道编号编码。

## 第一部分：第一信道，Session 状态信道

### 1.1 同步的是“发生过的事实”，当前状态是投影

候选定义：

- **History event**：设备对某次应进入 Session 历史的领域事实的不可变记录，有固定身份、内容及所属流；本文用于缓存、游标和重放的 event 均指这类记录。
- **Projection**：对事件进行归约后的当前 Session、turn、message/part、工具或输入请求状态，可以随新事件改变。
- **Snapshot**：某个明确游标处的 projection 快照，用于启动、恢复和缓存；不是偷偷修改过去的 event，也不是凭空补齐缺失历史。
- **Temporary live message**：逐 token、逐 chunk 或尚未定稿的实时内容，归入第三类临时消息责任，不是不可变历史；具体格式、订阅生命周期及恢复方式留待后续讨论。

例如：某次执行状态变化若属于约定的历史事实，就追加记录，不修改旧记录。文本逐步生成时则不为每个中间文本追加历史；在达到约定的历史记录边界时，再发布相应内容记录。

同一 message/part 的实时预览可以逐步增长；已发布的历史记录不再覆写。后续真正的消息修订可以用新历史事实表达，但不能将每个流式片段当作一次历史修订。“哪些状态转换、工具交互或内容边界进入历史”需要逐类定义，不等于只保留 assistant 的最终答案，也不等于必须等整个 turn 完成。

### 1.2 三层保持独立

| 层 | 承担什么 | 不承担什么 |
| --- | --- | --- |
| Wire envelope | 连接、消息类别、传输关联、确认与恢复控制；明确区分历史、RPC 与后续临时实时消息 | 不定义用户任务是否完成 |
| 领域 event | Session/消息/工具/输入交互发生的事实 | 不定义气泡、折叠或 UI 分组 |
| UI projection | 从事实投影出界面及交互状态 | 不凭用户发送动作确认 Agent 已收到，也不反向生成权威历史 |

第一、第三信道的业务消息都只上行。历史读取、resume/replay 请求，以及如需回传的应用级 ACK，均由第二信道承载；具体方法与确认语义待定。第三信道的订阅/取消订阅也经第二信道发起。WebSocket/tRPC 自身的传输保活与底层控制帧不属于这三类领域业务消息。

### 1.3 最小身份与顺序：候选规则

区分四种身份，不合并：

| 概念 | 候选含义 |
| --- | --- |
| `streamId` | 一条可独立排序、重放的事件流；示例暂按 Session 流表达 |
| `eventId` | 一次不可变事实记录的身份，重试和重放不变 |
| `sequence` | 该流中的逻辑位置，不使用墙钟时间代替 |
| `sessionId/turnId/messageId/partId` | 被事件描述的领域对象身份；多个 event 可指向同一对象 |

尚未决定：每设备一条流还是每 Session 一条流；Session 身份在设备/provider 之间怎样命名；序号由 provider、Connector 还是其他来源规范化。多写入者、来源切换与重新导入历史的边界必须在冻结规则前明确。

单 Session 流不能凭空表达设备的完整 Session 清单。Session 发现可使用设备目录流，或带覆盖范围与基准的目录快照；删除/消失不能仅由一次清单缺项推断。这是配套同步边界，尚未选择方案。

**候选不变量：**

1. 同一流内同一 eventId 重传时，内容及位置完全一致；冲突显式报错，不能 upsert 成另一条事实。
2. 一个已发布的流位置只能绑定一个 event；时间戳仅用于发生时间和展示，不作为可靠游标。
3. 收到新 event 才更新当前投影；客户端可展示 pending 输入，但 pending 不进入已确认事件历史。
4. 跨流不承诺全局总顺序。需要关联时用明确的领域 ID 或因果关联，而非靠时间猜测。

### 1.4 第一信道支持的 events：类型与职责

本节保留早期展开，供追溯语义覆盖；按奥卡姆剃刀原则精简后的独立评审见 [第一信道最小候选与现有功能对照](./Session-State-Channel.md)。下列细分名称不是本期最小集合建议，也不是已批准契约。

以下为候选类型清单，只定义职责，不展开字段或 schema。三信道划分已明确，但具体事件名、必需能力与 provider 映射尚未逐项确认。不要求 provider 虚构没有观察到的历史事实。

#### A. Session 与执行事实

| 候选 event 类型 | 职责 | 语义边界 |
| --- | --- | --- |
| `session.created` | 记录 Session 创建事实，建立其身份及初始归属 | 首次发现已有 Session 不等于刚创建；发现通过目录同步表达 |
| `session.metadata.changed` | 记录标题、父子关系等领域元数据变化 | 不承载中继缓存命中、连接健康等运行信息 |
| `session.execution.changed` | 记录 Session 执行状态的领域转换，如运行、等待、空闲或失败 | 不把设备离线当作 Agent 停止；不把 idle 当作人工任务完成 |
| `session.lifecycle.changed` | 记录明确的关闭、归档等生命周期变化 | 目录缺项、读取失败或缓存淘汰不能推断 Session 被关闭或删除 |
| `turn.started` | 记录一轮 Agent 执行开始，关联其输入及后续产出 | 不以一次 RPC 请求代替 turn；关联层级与 provider 支持待定 |
| `turn.finished` | 记录该轮执行终态，区分完成、失败或取消 | 命令接纳或取消请求接纳不是本事件；完成不等于人工任务验收 |

这些状态转换只有在来源能提供相应历史事实时才进入历史流。恢复连接后只知道“当前正在运行”，应发布下文的当前状态观察，不能补造未知的开始、等待或恢复历史。

#### B. JSONL 级内容与交互事实

| 候选 event 类型 | 职责 | 语义边界 |
| --- | --- | --- |
| `message.recorded` | 记录已达到历史粒度的 user、assistant 或 system 消息 | user 消息是设备确认的事实，不是前端发送动作；角色与内容格式分别解释 |
| `message.part.recorded` | 当来源提供稳定内容分段时，记录消息中的一个历史 part | 不记录 token/chunk；与整条 message 的组合规则待定，不能双重追加相同内容 |
| `tool.call.recorded` | 记录工具调用及其参数等调用语义 | 工具调用不是普通 assistant 文本；不强制保留每次进度更新 |
| `tool.result.recorded` | 记录工具结果及成功、失败或取消的结果语义 | 与调用关联，不以“工具成功”的展示文字替代实际结果 |
| `input.requested` | 记录 Agent 提出的用户输入请求 | 区分提问、选择与其他输入要求；普通发消息命令不自动成为回答 |
| `input.answered` | 记录设备已接纳的、与请求对应的回答 | 不等于第二信道的 RPC result；保留回答事实而非仅覆盖原提问 |
| `input.resolved` | 记录输入请求已结束，如已解决、撤销或过期 | 不替代回答内容；解决原因与 provider 支持待定 |
| `error.recorded` | 记录应进入 Session 历史的 Agent/工具链执行错误 | 不承载 RPC 参数错误、中继连接错误或回源失败；不自动推断整个 Session 失败 |
| `message.revised` | 来源确有正式历史修订时，追加修订事实并关联旧内容 | 可选扩展，不修改旧 event，也不把流式增长当作修订 |

`message.recorded` 与 `message.part.recorded` 是待收敛的层级表达，不预设所有 provider 都必须支持 part。活动提示只有在来源将其作为历史记录时才需映射；短命进度与 token 归第三信道，不默认增加持久 activity 日志。

#### C. 第一信道的同步消息，不是领域历史事实

| 候选同步类型 | 职责 | 与历史的边界 |
| --- | --- | --- |
| `sessions.snapshot` | 同步设备可发现的 Session 目录及明确覆盖范围，支持初始化与重新发现 | 发现不补造创建事实；缺项语义需明确，不直接删除历史 |
| `session.state.observed` | 同步当前执行状态、可写能力、待回答请求及状态可信度 | 当前观察可刷新或过期，不冒充完整状态转换历史，不占历史事实游标 |
| `history.batch` | 原样传送一段 JSONL 级历史，供初始化、补洞或重放 | 包装已有事实，不产生新 event 身份；实时与回源去重规则一致 |
| `history.snapshot` | 提供明确历史基准处的派生投影，以加速状态恢复 | 不替代完整 transcript，也不伪造此前事实 |
| `history.watermark` | 说明某个覆盖范围已同步到的位置及追赶进度 | 必须区分来源已知水位、接收水位与归约完成水位；不是新领域 event |
| `history.unavailable` | 明确回源不可用、历史缺口或无法继续恢复的范围 | 不返回成功形状的空历史，不把缓存淘汰当作 Session 删除 |

该分组避免把第一信道所有消息都误称为“不可变 event”：其中领域历史记录不可变，目录/当前观察是同步材料，批次/水位/不可用是同步协议信息。这些消息均上行；触发同步的下行请求属于第二信道。它们不会因此成为第三信道的可订阅 token。

逐 token、逐 chunk 的流式中间状态已明确不进入历史。短命打字指示、连接健康等其他信号的归属仍未决定。若提供 ephemeral 实时观察，它们必须与可重放事实明确区分，不能让历史恢复依赖已丢失的观察。

### 1.5 小示例：历史内容记录，不是流式中间更新

下面示意一个已达到历史记录边界的 assistant 内容，不要求一个 part 必须等到整个 turn 完成。字段和命名仍为候选。

```json
{
  "kind": "state.event",
  "streamId": "device-1:session-1",
  "eventId": "event-17",
  "sequence": 17,
  "event": {
    "type": "message.part.recorded",
    "sessionId": "session-1",
    "messageId": "message-1",
    "partId": "part-1",
    "role": "assistant",
    "content": { "format": "markdown", "text": "测试已通过。" }
  }
}
```

此前生成过的“测”“测试已”等预览文本不进入历史流，也不占用历史 sequence。历史与实时同步路径都应将这份历史记录识别为同一事实，重复送达不新增记录。

之后的实时预览由第三类临时消息责任承载，不要求重放旧预览。它由第二类命令责任控制订阅，不与第一类不可变历史混用。预览和历史可能交错到达，旧预览不能覆盖已确认的历史内容，具体协调方式留作后续 TODO。

**传输 batching、压缩、聚合快照可以优化，但不能把发布过的历史 eventId 绑定到不同内容。** 一次历史记录的边界、取消或失败时已生成部分内容是否成为历史记录，尚需进一步定义。

### 1.6 缓存与恢复：不可变性提供什么

候选同步语义；下行控制走第二信道，上行状态与历史数据走第一信道：

| 控制操作 | 含义 |
| --- | --- |
| resume | 第二信道请求恢复，声明同步范围及已连续归约的游标；不等于第三信道实时订阅 |
| event / event batch | 第一信道上行传递新事件或原样重放历史事件 |
| ACK / watermark | 第一信道水位报告与第二信道应用级确认分别定义；收到、持久化及归约完成不得混用 |
| replay / range | 第二信道请求某段缺失历史，不创作领域事实 |
| snapshot | 第一信道上行提供明确基准游标处的派生状态及覆盖范围 |
| gap / reset-required | 第一信道上行告知无法恢复的范围，不返回“看似完整”的历史；RPC 请求被拒绝则用第二信道 error |

候选缓存规则：

- 设备、中继、客户端可按稳定 stream 身份和事件区间缓存不可变记录；缓存身份须包含访问主体与来源边界，不能跨账号或新设备身份误复用。
- 幂等去重后才归约。乱序到达可暂存，不能把“见过的最大 sequence”当作“连续处理完成的游标”。
- 快照只能与其基准兼容的后续事件拼接。仅当前状态快照能恢复当前视图，不自动恢复此前完整 transcript。
- 中继缓存命中可避免回源；未命中是否能回源，取决于设备/provider 是否保有可重放的相同历史。
- 历史补传与实时发布的历史记录使用同一身份、同一归约语义；provider 可恢复的历史不包含流式中间状态是符合本轮方向的，不需伪造或补录这些预览。

### 1.7 已明确：整 Session 缓存、整 Session 淘汰

中继缓存可以淘汰，但不得因容量或时间策略仅删除某个 Session 的早期事件，再保留尾部并将其作为该 Session 的完整缓存。例如可以淘汰 Session A 的整份缓存，同时保留 Session B；不能把 A 的事件 1–100 删除，只保留 101–200。

缓存的完整性与淘汰粒度是两件事；这里的“完整”针对约定粒度的历史记录，不要求保存流式预览：

- **已缓存完整历史的 Session**：保留起点到已知连续水位的历史，并继续接收新事件；“完整”不意味着已收到尚未到达的最新事件。
- **正在回源或存在缺口的 Session**：明确标注覆盖范围和加载/缺失状态；不能因为只有尾部事件就宣称完整。
- **已淘汰 Session**：视为缓存未命中，依赖设备重建；设备不可用时明确告知历史暂不可读取，不伪装成空 Session 或成功恢复。

由此提出以下配套候选规则，具体机制尚未定稿：

1. 淘汰时一并失效该 Session 的历史缓存、依赖它的快照/投影及缓存恢复基准；不能保留“历史仍完整可用”的标记。设备目录中的发现信息可独立存在，但不表示历史仍在缓存。
2. 重新缓存需要恢复该 Session 的完整历史覆盖，不能仅从已失效的旧游标继续拼尾部。分批、分页回源可以进行，但在完整前必须显式呈现部分覆盖。
3. 前端自己仍保有的完整缓存不会因中继淘汰而自动失效；前端可凭自己实际保有的连续历史恢复，而不能依赖中继已不存在的基准。客户端自身淘汰也建议遵守整 Session 规则，适用范围待进一步明确。
4. Session 历史缓存淘汰不等于关闭 Agent Session、删除设备原始历史或清除命令去重/结果记录；这些具有独立生命周期。

**不可变 ≠ 必须永久保存；缓存也不等于只能存内存。** 缓存可以跨进程持久保存，但仍可按 Session 整体淘汰，不因此升级为权威历史承诺。缓存配额、选择淘汰哪个 Session、离线命中缓存的可读性、账号退出/删除时的清理及敏感内容政策尚未决定。容量不足时选择不缓存或整 Session 淘汰，不能静默采用尾部保留。

## 第二部分：第二信道，命令信道

### 2.1 典型 RPC，但与状态事实分离

逻辑路径：前端发起意图 → 中继路由 → 设备执行 → 结果经中继返回。中继转发不代表中继执行 Agent 工作；命令也不是前端向 event stream 直接追加记录。

候选 RPC 要素：

- 稳定 `requestId`，明确目标设备/Session、方法与类型化参数。
- result 或结构化 error，与原 requestId 对应。
- 必要时提供 accepted/progress 等非终态观察；它们不替代终态 result。
- 显式定义每个方法的“成功”边界：已接纳、已提交给 provider，还是执行完成。
- 断线/超时可能意味着结果未知，不等于已失败或未执行；非幂等命令不能盲目重试。

请求关联 ID 不自动带来 exactly-once。重试是否复用 requestId、谁保留去重记录、保留多久、能否查询结果，都是待定规则。异步长任务可在 RPC 返回 execution/turn ID 后，由状态事件流持续报告生命周期。

### 2.2 命令范围：候选清单

| 候选方法 | 目标与参数语义 | 候选成功边界 | 讨论优先级 |
| --- | --- | --- | --- |
| `session.create` | 在指定设备/provider 创建 Session，可带初始输入 | 返回新 Session 身份及创建操作结果；不宣称初始回答完成 | 核心候选 |
| `message.send` | 给已有 Session 发送用户内容 | provider 已接纳；后续执行靠事件流 | 核心候选 |
| `input.respond` | 对明确 inputRequestId 提交类型化回答 | 回答被接纳；不宣称 Agent 已继续或完成 | 核心候选 |
| `execution.cancel` | 取消明确 turn/execution | 返回取消请求是否被接纳；取消事实靠事件流确认 | 核心候选 |
| `session.close` | 结束 Session 生命周期 | 方法须定义“请求接纳”或“已关闭” | 扩展候选；不同于取消一次执行 |
| `session.configure` | 修改模型/provider 配置等 | 明确哪些配置立即或下一 turn 生效 | 扩展候选 |
| `session.describe` / `sessions.list` | 主动查询当前状态或可发现 Session | 返回带基准/覆盖范围的观察 | 可选查询；不能形成与事件流冲突的第二权威 |
| `command.getResult` | 查询已发命令的结果或结果未知 | 返回准确的执行观察 | 恢复候选；取决于结果保留责任 |

每个设备/provider 声明方法能力与参数限制，不能仅有笼统的“支持发消息”。不支持的方法明确返回 unsupported；不能默默把结构化 input.respond 降级成普通文本。

实时更新的订阅/取消订阅也属于命令通道的未来控制操作，但本期不加入必需命令集合；方法名、参数和完成语义均未定稿，见后续 TODO。

当前 `session.history` 的意图是读取历史。理想模型中，读取或重放请求属于第二信道的同步控制命令，历史数据则通过第一信道上行；请求结果与数据覆盖水位的关联仍待定义。读取历史不等同于让 Agent 执行新工作。

本轮不默认加入文件修改、Shell 执行、权限自动批准、删除持久历史或 provider 所有原生操作。

### 2.3 小示例：命令成功与事件确认

```json
{
  "kind": "rpc.request",
  "requestId": "request-1",
  "target": { "deviceId": "device-1", "sessionId": "session-1" },
  "method": "message.send",
  "params": { "content": { "format": "text", "text": "继续检查测试" } }
}
```

```json
{
  "kind": "rpc.result",
  "requestId": "request-1",
  "result": { "disposition": "accepted" }
}
```

之后设备流追加“用户消息被接纳”的领域事件，可带 `causedByRequestId: "request-1"` 关联。该事件是设备观察到的事实，不是原请求帧的简单镜像；不同 provider 可能无法提供该关联，应通过能力及映射边界说明。

RPC 返回与状态事件到达前端的先后顺序不应预设。即使物理连接帧有顺序，缓存、独立消费者和异步执行仍会造成观察交错。UI 使用 requestId 关联 pending 与已确认内容，避免重复气泡；这属于 projection，不改变事件身份。

### 2.4 三类失败必须分开

| 失败类别 | 含义 | 后续动作边界 |
| --- | --- | --- |
| RPC error | 方法不存在、参数不合法、无能力、命令被拒绝等 | 请求层处理，不伪造 Agent 历史错误 |
| 命令结果未知 | 断线或超时，无法确认是否执行 | 查询、去重恢复或人工处理，不自动判失败重发 |
| Agent 执行失败 | 已接纳工作后来失败 | 状态流追加执行错误/终态事实，不改写先前 RPC 接纳结果 |

## 后续 TODO：第三信道，可订阅消息信道

**用户已明确三信道划分，第三信道功能本期不实现。** 可订阅消息信道与 Session 状态信道、命令信道并列，在同一 WebSocket 上承载临时实时消息：

1. 前端意图经中继，通过命令通道请求订阅某个 Session 的实时 update。
2. Connector 在对应订阅下，将该 Session 的实时 token 等临时消息上行至中继，再供前端消费。

临时消息不进入不可变历史，不占历史游标，不属于整 Session 历史缓存的完整性要求。临时消息的缓冲、丢弃与短期保留规则另行定义，不把历史的整 Session 淘汰约束直接套在实时 token 上。
