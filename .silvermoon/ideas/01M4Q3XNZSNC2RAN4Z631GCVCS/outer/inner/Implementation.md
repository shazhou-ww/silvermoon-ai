# Implementation

本契约为准备阶段的轻量初版；具体 schema、兼容策略和改动范围在实施阶段按已接受构想细化。

## Steps

### I-S01: 固定协议与映射

按下行（Relay Service → Connector）请求共同细化输入、上行（Connector → Relay Service）反馈、续推及失败边界，形成版本化 schema、provider 能力映射和兼容规则；以 target + 观察基准表达范围与恢复，以 requestId 关联多包，以有序 eventId 合并身份与位置，保留临时更新的独立版本及显式缺失语义。

### I-S02: 贯通状态与命令链路

在 Connector、Relay Service 和 Web 消费链路中实现统一读取与操作反馈，支持 requestId 下多包 events 组装及有界续推；区分首包到达、声明覆盖完成和续推结束，保留旧客户端及旧 id/sequence 的映射兼容边界，不引入长期订阅状态机。

### I-S03: 验证恢复与跨 provider 行为

用针对性测试覆盖多包重复/乱序、跨 requestId 补拉、同编号内容冲突、来源重建或编号重置、续拉/续推重叠、等待超时与临时缓冲过期；保留断线、整 Session 淘汰、操作与事实交错及续推关闭的恢复验证。

## Acceptance criteria

### I-AC01: 契约可追溯

通过 schema、源码引用和映射测试证明每类获准请求及其反馈、续推与失败边界可追溯，有明确生产者、消费者与 provider 能力边界，且无未说明的默认映射。

### I-AC02: 历史恢复可验证

通过自动化测试证明有序 eventId 在同一 target 来源范围内稳定、跨请求重复与重放幂等、冲突显式失败；多包缺口不按最大编号推进基准，来源重置使旧基准失效，丢弃或关闭续推仍可恢复；等待超时、整 Session 淘汰、回源不可用与临时更新过期不伪装成完整历史。

### I-AC03: 命令语义保持独立

通过协议与集成测试证明 requestId 可关联首包、后续包及续推而不代替事实身份或操作因果关联；操作结果与状态事实可交错，停止观察不终止 Agent；旧客户端兼容且续推资源在约定边界内释放。
