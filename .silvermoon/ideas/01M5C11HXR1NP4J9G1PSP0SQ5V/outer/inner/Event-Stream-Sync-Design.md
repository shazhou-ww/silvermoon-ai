# 通用事件流同步技术方案：连接与消息原语

## 文档定位

本文件是 [Implementation.md](Implementation.md) 的支持文档，记录连接、消息与分包方案，不是独立验收契约或已实施能力。用户已要求按本轮确认的方向推进实施并授权主 Agent 审查各阶段；精确生命周期与验证结果以 CLI、当前契约和证据为准。本轮仅覆盖 Connector 与 Service 的通用同步底座，不设计新 UI。

项目方向从统一 coding session Relay 转向理解 Agent 驱动的自治设备。Session 与 Supervisor / Objective 可以共享事件同步机制，业务适配和投影负责解释事件。底座剥离业务语义，但保留明确的同步语义。

## 现状与技术选择

当前使用 Node.js、Cloudflare Workers、Durable Objects、D1 和 WebSocket / tRPC：

- [Connector](../../../../../packages/connector/src/connector.ts) 已有保活、重连和重新注册机制，但离线事件缓冲是有限内存队列，满时会丢弃旧观察。
- [RPC 定义](../../../../../packages/rpc/src/index.ts) 直接暴露 `syncSessions`、`sessionUpdated`、`sessionEvent` 等业务操作。
- [连接路由](../../../../../apps/worker/src/index.ts) 按 token ID 定位 DO，而事件实际写入 D1。
- [事件写入](../../../../../apps/worker/src/connector-session.ts) 在冲突时更新内容，不能直接作为不可变事件日志。
- [WebSocket 桥接](../../../../../apps/worker/src/trpc-websocket.ts) 使用事件监听器和内存中的处理上下文，新同步协议需要另外明确休眠和重建后的恢复行为。

因此，泛化不是简单重命名 `sessionId`。优先复用现有平台，不引入 NATS、Kafka 或 MQTT 集群；这些组件不直接替代当前部署中的设备同步契约。

新增精简、显式的 WebSocket 同步协议，保留旧 Session tRPC 通道作为兼容路径。服务端按 DO 原生 WebSocket 事件模型设计，实施前核验休眠 API、存储事务语义、资源限制及成本。本轮未成功获取最新 Cloudflare 在线文档，本文不承诺具体平台额度或 API 细节。

## 职责与存储边界

```text
Session / Supervisor 等业务生产者
             |
      业务适配与本地可靠日志
             |
      Node.js Connector
             |
   一条 WebSocket，多条逻辑流
             |
       DeviceSync DO
       - 连接与写入租约
       - 不可变事件日志
       - 读取与订阅
             |
       业务投影消费者
             |
       D1 等查询存储
```

| 部分 | 职责 | 不承担 |
| --- | --- | --- |
| Connector | 读取本地可靠事件、连接、补传、同步进度 | Session 或 Objective 的业务解释 |
| Service / DO | 认证与权限、流身份、追加去重、持久确认、读取和订阅 | Supervisor 决策或业务对象状态计算 |
| 业务适配与投影 | 生产事件、重建状态、解释关联与新鲜度 | 另行实现可靠传输 |

第一版以账户下的设备作为物理协调单位，一个 `DeviceSync DO` 承载多条逻辑流。DO 身份由稳定的账户和设备身份确定，不随 token 轮换改变。

逻辑流是独立命名、排序和续传的单位；物理 DO 是连接、协调和存储的分片单位，两者不等同。不建立全局 DO，不承诺单设备无限吞吐。按流进一步分片留待实际负载证明其必要性。

新日志及流头位置保存在所属 DO 的 SQLite 存储中；D1 保留账户、设备、凭证及可重建的查询投影。追加与业务投影不做跨存储双写事务。中心已持久保存但投影滞后，是可恢复状态，不要求生产者重新制造业务事实。

## 流与事件身份

- 每条流由所属设备的当前有效 Connector 单写。
- 事件身份为 `(accountId, deviceId, streamId, seq)`。
- `seq` 从 1 开始、流内连续递增，以十进制字符串传输，避免跨语言整数精度问题。
- 仅保证流内顺序，不建立跨设备或跨流全局顺序。
- 重连、进程重启和凭证轮换不重置流身份或事件序号。
- 原业务对象可以改变，但已追加事件不可修改；变化通过后续事件表达。

最小事件结构示意：

```ts
type EventRecord = {
  seq: string;
  payload: string;
};
```

`payload` 是不透明 UTF-8 内容。业务类型、业务发生时间、内容版本和对象关联由业务层编码。`streamId` 位于请求或批次信封中；服务端接收时间是附加元数据，不代替业务发生时间。

流创建时可记录不可变的 `contentType` 或格式标识，底座只保存并转交。可变名称和对象发现信息可由业务目录流表达；底座不提供可任意覆盖事件内容的接口。

## 连接原语

### 生命周期与握手

```text
DISCONNECTED -> CONNECTING -> NEGOTIATING -> READY
      ^                            |          |
      +-------- 断线 / 超时 / 重试 -+----------+
```

`READY` 只表示握手成功，不表示历史已追平或业务观察新鲜。

| 原语 | 方向 | 含义 |
| --- | --- | --- |
| `hello` | 客户端到服务端 | 协议版本、客户端实例和所需角色 |
| `welcome` | 服务端到客户端 | 协商版本、连接 ID、限制与写入资格 |
| `ping` / `pong` | 双向 | 链路活性，不推进业务事件或观察时间 |
| `error` | 服务端到客户端 | 结构化失败及恢复条件 |

认证在 WebSocket 升级阶段完成，账户、设备和授权范围由服务端绑定，不信任消息中自报身份。读连接同样受账户与设备范围授权。

`requestId` 仅在连接内关联请求和响应，不是持久幂等键。握手有超时限制，未进入 `READY` 的连接不得追加或订阅。

### 写入租约与旧连接隔离

- 同一设备只有一个有效写入连接，允许多个受权读连接。
- 写入连接仍有效时，新写连接收到 `writer_busy`，不静默抢占。
- 租约释放或失效后，新连接取得新的写入代次。
- 每次追加检查有效写入代次，旧连接即使迟到也不能继续写。
- 代次和租约正确性不只依赖内存；DO 重建后必须仍能隔离旧写入者。
- 连接 ID 和代次是临时会话信息，不属于事件身份，也不能改变已保存事件内容。

网络错误采用带随机抖动的退避重连；凭证撤销、版本不兼容等错误停止自动重试并报告。心跳间隔、超时与租约时长需在实施时统一确定，不能承诺瞬时判断设备离线。

## 消息原语

| 原语 | 职责 | 持久状态影响 |
| --- | --- | --- |
| `stream.open` | 创建或打开流，返回提交位置及保留范围 | 首次创建时改变 |
| `stream.list` | 分页列出有权访问的流 | 无 |
| `stream.append` | 原子追加一批连续事件 | 追加日志和推进流头 |
| `stream.read` | 从指定位置分页读取 | 无 |
| `stream.subscribe` | 从指定位置追赶历史并持续跟随新增事件 | 仅连接态 |
| `subscription.ack` | 确认处理进度、释放发送窗口 | 第一版仅连接态 |
| `subscription.cancel` | 取消订阅 | 仅连接态 |

第一版不定义通用远程命令、跨流事务、多写者合并、全局排序或服务端持久消费组。现有 Session 命令继续由兼容业务层承载。

### 追加与持久确认

请求示意：

```json
{
  "type": "stream.append",
  "requestId": "r17",
  "streamId": "stream-a",
  "events": [
    { "seq": "41", "payload": "..." },
    { "seq": "42", "payload": "..." }
  ]
}
```

响应示意：

```json
{
  "type": "stream.appended",
  "requestId": "r17",
  "streamId": "stream-a",
  "committedThrough": "42"
}
```

要求：

1. 一批全成或全败，事件和流头在同一 DO 存储事务中提交。
2. 持久提交后才发送成功确认，不以收到网络帧或写入内存作为成功，也不等待业务投影。
3. 同位置、同内容重发视为成功，不重复保存。
4. 同位置、不同内容返回 `event_conflict`，绝不覆盖原记录。
5. 跳号返回 `sequence_gap` 和期望位置；批内必须连续，重复前缀与新增后缀均需验证。
6. 超限、磁盘或存储错误明确失败，不丢旧事件以返回成功。

按原始 UTF-8 内容判断一致性。Connector 保留原始序列化结果，不能在重试时生成新时间戳或改变 JSON 序列化结果。内容摘要可用于优化，不能替代明确的一致性契约。

第一版每条流最多一个在途追加批次，不同流有限并发，并限制帧、批次和连接的事件数与字节数；具体数值需结合平台限制与测试确定。

确认丢失后的恢复：

```text
设备发送 41、42
中心持久提交，确认丢失
设备重新连接
stream.open 返回 committedThrough = 42
设备核对本地记录与进度，从 43 继续
```

也可重发 41、42，通过幂等追加验证。不能仅凭中心更大的流头就删除本地未知内容；恢复以单写者身份连续、本地可靠记录未丢失为前提，矛盾时停止并报告。

保证是允许传输重试、通过幂等追加避免重复存储，不是业务端到端 exactly-once。

### 历史读取与连续订阅

位置 `after = N` 表示消费者已经处理完 N，接下来需要 N 之后的事件。初始位置为 `0`。

`stream.read(streamId, after, limit)` 返回有序事件、下一位置和当次观察的流头，事件数及字节数均有界。

`stream.subscribe(streamId, after)` 是一个连续操作：

```text
读取持久日志中的积压 -> 追到观察到的流头 -> 继续交付新增事件
```

不能先完成历史查询，再挂只接收新消息的监听器，否则两者之间可能丢事件。订阅保存下一个待发送位置，并持续从持久日志读取。新增通知仅唤醒读取，不承担可靠数据交付。

客户端收到的交付批次包含订阅 ID、事件位置及内容。服务端可报告 `caughtUpThrough`，只表示追到某次观察位置，不表示永远同步完成。

连接断开后，客户端从自己可靠保存的已处理位置重新订阅。DO 重建后不能依赖丢失的内存队列恢复历史；仍存续的休眠连接需要可恢复的连接附件与订阅状态，或显式终止并要求重订阅，不得假装订阅仍连续。

### 消费确认与背压

| 确认 | 意义 |
| --- | --- |
| `stream.appended` | 中心已持久保存生产者的事件 |
| `subscription.ack` | 消费者已处理交付内容，可释放发送窗口 |

窗口限制在途事件数和字节数。耗尽时暂停读日志，不无限缓存历史。确认绑定当前连接及订阅，只能推进到实际交付的位置；重复确认不能重复释放窗口。

慢消费者可被明确断开并续传，不能静默跳到最新。心跳不释放消费窗口。

第一版不持久化服务端消费组位置。消费者尽可能在同一事务中更新业务投影和本地处理位置，再发送确认。崩溃导致的重复交付由消费者按流和序号幂等处理，不能因为网络交付就认为业务处理完成。

## 本地可靠性与源端缺口

Connector 对生产者需要以下能力，而不只是瞬时 `onEvent` 回调：

- 枚举流。
- 按序号读取已持久化事件。
- 等待新增事件通知。

生产者已有可靠且可重放的本地日志时，可直接补读，不必再复制完整 outbox；只有实时通知时，适配器先写本地追加日志，再交给 Connector。

事件内容和序号必须先可靠保存再发送。中心未确认的事件不能因为内存满或进程退出丢失。源日志保留规则必须覆盖未确认事件；无法施加该保证的源端不能宣称无损同步。

若本地日志消失，或本地状态丢失导致原序号不可恢复，明确报告 `source_history_unavailable` 或 `local_state_lost`。不能重新编号并冒充完整原历史。确实无法延续时，显式创建新的流身份并由业务层表达连续性中断。

现有 Session 事件可能是可变内容投影，不能直接按原 ID 当作不可变事实导入。适配器需把后续观察或更新记录为新的不可变事件，并标明导入历史的来源和完整性；不能补造不存在的历史。

## 保留范围与错误契约

`stream.open` 至少返回：

- `committedThrough`：最高连续提交位置，初始为 `0`。
- `retainedFrom`：仍可读取的最早事件位置；空保留区间需明确表示。

消费者所需事件已被清理时返回 `cursor_expired` 及当前范围，不自动跳至最新。中心已经清理的事件无法再通过内容比较验证重发；第一版明确报告 `history_unverifiable`，不将未知内容静默确认成功。

保留策略须与补传、恢复承诺一起确定；不可变不等于永久保留，也不等于必须上传所有本地数据。敏感字段过滤由业务生产者或适配器负责，底座仍强制身份隔离、授权和资源限制。

| 错误码 | 恢复含义 |
| --- | --- |
| `unsupported_version` | 升级或使用兼容端点，不循环重试 |
| `writer_busy` | 等待现有写入租约释放或失效 |
| `stale_connection` | 当前连接失去写入资格，重新握手 |
| `stream_not_found` | 核对流身份；不得读取时泄露其他账户信息 |
| `event_conflict` | 停止该流，核对身份和本地日志，不覆盖历史 |
| `sequence_gap` | 从期望位置补传 |
| `cursor_expired` | 历史已裁剪，显式处理业务恢复 |
| `history_unverifiable` | 所需旧内容不可核对，不静默确认 |
| `payload_too_large` | 调整记录或批次；单条超限不得静默截断 |
| `quota_exceeded` | 明确资源边界及可重试条件 |

错误包含关联请求或订阅、失败范围、是否可重试和必要恢复位置。协议级、连接级、流级故障需区分；流内容冲突不应无说明地伪装成设备离线。

## 分包策略

采用“复用现有运行包，只新增一个同步协议包”的边界。先隔离模块职责和依赖方向，不另起一套 Connector、Service 和 SDK。本节记录讨论确认的分包方向，实际交付与验证以[实施评审](Implementation-Verification.md)为准，不将原始草案中的能力假设视为验证证据。

### 包与应用职责

| 包或应用 | 职责 | 处理方式 |
| --- | --- | --- |
| `@silvermoon-ai/sync-protocol` | 通用事件同步的类型、消息结构、版本与校验 | 新增纯契约包 |
| `@silvermoon-ai/connector` | Node.js 同步客户端、本地事件源接入和 CLI | 复用，内部隔离同步核心与适配 |
| `@silvermoon-ai/worker` | Cloudflare 部署入口、身份授权、DO 同步实现和业务投影 | 复用，内部划分模块 |
| `@silvermoon-ai/protocol` | 现有 Session 业务模型与旧协议 | 保留兼容，不继续混入通用同步契约 |
| `@silvermoon-ai/rpc` | 现有 Session tRPC 契约 | 保留兼容，不扩张为通用同步层 |
| `@silvermoon-ai/web` | 产品界面与展示 | 本轮不调整 |

现有协议包已被 Session 与旧命令使用，直接改变其含义容易造成新旧语义混杂。新增小型同步协议包，让新旧链路并存，并能明确检查通用层是否仍依赖业务模型。

### 同步协议包

`@silvermoon-ai/sync-protocol` 定义 Connector、Stream、Event 的同步信封、握手、追加、读取、订阅、确认、错误、协议版本以及位置等字段规则。

协议包可依赖现有运行时校验工具，但不包含连接重试、本地文件或 SQLite 操作、Cloudflare DO 实现、Session 或 Supervisor 业务结构。它需要同时适用于 Node.js、Worker 和未来浏览器消费者，不依赖 Node.js 或 Cloudflare 专有 API。

共享的是双方通信契约，不是双方状态机的全部实现。不为此新增含义模糊的 `core` 或 `common` 包。

### Connector 内部分层

```text
Connector
  - sync       连接、握手、追加、续传、进度与背压
  - sources    本地事件源适配与必要的可靠日志
  - CLI        配置、凭证、进程生命周期与组装
```

同步核心只依赖通用事件源接口：枚举流、按位置读取持久事件、等待新增通知。它不知道上游是 VS Code 还是 Supervisor，不猜测或制造业务历史。

VS Code 适配器理解 AHP，Supervisor 适配器理解生产端事实；两者将业务观察转换为不可变事件。源端没有可靠日志时，适配层先持久化再供同步核心读取。

适配器依赖同步接口，同步核心不反向依赖适配器。首版通过内部模块和明确导出入口隔离，不为每个适配器创建独立 npm 包；只有独立依赖、发布或维护需求成立时才拆包。

现有 Connector 已公开导出 VS Code Provider，迁移保留旧公共入口，并提供独立的通用同步入口，不能静默改变已有用户的 API。具体入口名称在实施时确定。

### Worker 内部分层

```text
Worker
  - identity / auth    账户、设备、凭证与授权
  - sync               DO、不可变日志、连接与订阅
  - session            旧业务接入、命令与查询投影
  - supervisor         后续业务接入与查询投影
```

同步模块通过明确接口使用身份和授权，不解释 Session 或 Supervisor。业务投影消费日志，不进入事件追加事务。

当前只有一个 Cloudflare 服务消费者，不新增 `sync-server` 框架包，不提前引入跨平台存储抽象。先在 Worker 内保持清晰模块，实际出现第二个服务实现或独立复用需求后再评估提取。

### 依赖方向与发布边界

以“调用方依赖被调用方”表示：

```text
Connector 同步核心 -> sync-protocol
Worker 同步模块    -> sync-protocol
本地业务适配       -> 同步接口 + 自身业务模型
服务端业务投影     -> 日志消费接口 + 自身业务模型
```

通用同步层不能依赖 Session、Supervisor 业务模型，也不能导入对端实现代码。旧协议与 RPC 包继续服务兼容路径，迁移完成后再评估收缩或更名，不为了命名整齐先进行广泛重构。

不新增第二个 Connector 产品包，避免两套配置与连接生命周期。不提前创建浏览器 SDK；存在真实直接订阅需求时再提取环境适配的客户端，浏览器不能导入 Node.js Connector。

Connector、Stream、Event 是模型层次，不是三个发布单元。仓库分包也不等于 npm 发布：新协议包可先作为私有 workspace 包使用，独立公开发布由外部使用需求决定。现有公开 Connector 的构建产物和依赖必须保持可安装，不能让未发布的 workspace 包成为无法解析的运行时依赖。

## 迁移与验证重点

先以不带 Session / Supervisor 语义的生产者和消费者验证协议，再接入业务适配。保留旧客户端路径，不做无法原子保证的跨 D1 与 DO 双写确认。

实施时将必要步骤和验收证明细化进 Implementation 与 ledger，本文不另设执行清单。重点覆盖：

1. 中心提交后确认丢失，重连不重复保存；同序号不同内容被拒绝。
2. Connector 崩溃后未确认事件可恢复；源端缺口不返回成功。
3. 追赶历史期间持续追加，无缺口且流内有序。
4. 慢消费者与多流并发下内存有界、单流顺序不变、可断线续传。
5. 旧写入者、凭证轮换、DO 重建和休眠不会改变流身份或绕过隔离。
6. 保留范围变化、超限、存储失败和跨账户访问明确失败。
7. 业务投影可从日志重建，并与旧 Session 功能兼容。

待实施前核验的具体项包括：协议字段与完整校验结构、订阅恢复附件、租约持久化与检查顺序、事务和输出持久性保证、配额与保留数值、消费者连接路由及设备规模下的分片成本。草案中的能力不是现有实现的验证结果。
